## 2. Package metadata and build/install hooks

**Confirmed (benign):**
- Build backend `poetry-core>=2.0.0`, no custom build script: `pyproject.toml:33-35`. `[tool.poetry]` only has `packages = [{include = "src"}]` (`pyproject.toml:37-38`) — no `build =` key, so no project-owned code runs at build/install time. `poetry-core` itself is fetched with only a lower bound (`pyproject.toml:34`) by any `pip install git+…` consumer (standard PEP 517 behaviour).
- Console script `claude-telegram-bot = "src.main:run"` (`pyproject.toml:30-31`). The top-level package is named the generic **`src`** (`pyproject.toml:38`); it will collide with any other distribution that installs a top-level `src` package into the same environment (low; no exploit shown).
- `anthropic = "^0.40.0"` is declared (`pyproject.toml:49`) and locked at 0.40.0, but nothing in `src/` imports it (`grep -rn "import anthropic" src` → none): unused dependency that only enlarges the surface.
- `setup.cfg` contains only flake8 config (`setup.cfg:1-3`).

**Makefile:**
- `make install` runs `poetry install --no-dev` (`Makefile:24`); `--no-dev` was removed in Poetry 2.x (project requires poetry-core ≥2, `pyproject.toml:34`), so this target probably fails on current Poetry (functional note; not executed).
- `make dev` runs `poetry run pre-commit install --install-hooks || echo …` (`Makefile:28`); `pre-commit` is not a declared dependency and no `.pre-commit-config.yaml` exists. A stray `pre-commit` on `PATH` would run; low.
- `run-remote` calls `security unlock-keychain` + `tmux` (`Makefile:58-59`), local operator convenience, no downloads.
- `bump-*`/`release` do `git push` + tag push (`Makefile:75-105`); the tag push triggers `release.yml` (§5).
- No `curl`/`wget`/`pip install` in the Makefile.

### 5.2 Findings

**F1 — CI ignores the lock file (Confirmed, Medium).** `.github/workflows/ci.yml:35`: `run: poetry lock && poetry install`. This re-resolves every dependency from PyPI at CI time, discarding the committed hashes; CI therefore tests/lints against versions not recorded in `poetry.lock`, and a malicious or broken release inside a declared range (e.g. `claude-agent-sdk ^0.1.39`, `fastapi ^0.115.0`) executes on the runner when `pytest`/`black`/`flake8` import it. Upstream already fixed the same problem in `release.yml:36` (`poetry install --no-interaction`; commit `ce84600` message: "Change CI from `poetry lock && poetry install` to `poetry install --no-interaction` for reproducible builds") but **`ci.yml` was missed**. The `actions/cache` key hashes `poetry.lock` (`ci.yml:32`) while the venv is built from a regenerated lock, so a cached `.venv` can be stale relative to its key. Blast radius is limited: fork PRs receive no secrets and a read-only token by default.

**F2 — Mutable action tags; broad write token (Confirmed, Medium).** Every `uses:` is a tag, none a commit SHA (`ci.yml:15,18,23,29`; `release.yml:16,19,24,30,52,61`; `claude.yml:29,35`). A retargeted tag in any of `snok`, `softprops`, `anthropics` (third-party repos) runs in the job. In `release.yml`, `permissions: contents: write` is set at **workflow level** (`:8-9`), so the `test` job — which runs `poetry install` of third-party code (`:36`) and whose checkout persists credentials — also holds a write-capable `GITHUB_TOKEN`; only the `release` job (`:47-73`) needs it. `ci.yml` has no `permissions:` block, so its token scope depends on the repository/org default (not visible from files; **unverified**). Mitigation: SHA-pin, job-level `permissions`, `persist-credentials: false`.

**F3 — Unpinned Poetry bootstrap (Confirmed, Low–Medium).** `snok/install-poetry@v1` is used with no `version` input (`ci.yml:23-27`, `release.yml:24-28`). The action's default is `version: latest` (action.yml on `main`). Its `main.sh` downloads `install-poetry.py` from `raw.githubusercontent.com/python-poetry/install.python-poetry.org/<commit d7fd0502ef807e711f65204b1ab39c1a1e23c69c>` (installer commit **is pinned** — good), then installs the *latest* Poetry from PyPI. I read `main`, which may differ from the `v1` tag actually executed (**unverified for tag `v1`**). Result: CI behaviour depends on whichever Poetry is current. Expected third-party traffic, but not integrity-pinned.

**F8 — `claude.yml` secret exposure model (Risk requiring configuration, Low–Medium).** Anyone can trigger the job by commenting/opening an issue containing `@claude` in a public repo (`claude.yml:15-19`; no `author_association` filter). The job holds `CLAUDE_CODE_OAUTH_TOKEN` (`:37`) and `id-token: write` (`:25`). Per the action's docs (https://github.com/anthropics/claude-code-action/blob/main/docs/security.md, read from `main`): the action "can only be triggered by users with write access to the repository" for issue/PR/comment/review events, and bots are excluded unless `allowed_bots` is set (not set here). So protection rests on the third-party action's gate, not on this workflow's `if`. **Unverified:** that `@v1` today behaves per that doc, and that the secret/Claude app exist on the fork (not visible from files). GitHub-side permissions are read-only (`:22-26`), limiting damage from prompt injection, but the OAuth token is in the agent's environment by design. Recommended: add an `author_association` check, keep `allowed_bots`/`allowed_non_write_users` unset, SHA-pin, or disable the workflow if unused.

**F9 — Disabled `pull_request_target` workflow (Risk if re-enabled; High if enabled).** `claude-code-review.yml.disabled:4-5` uses `pull_request_target` (base-repo secrets) and checks out `refs/pull/<n>/merge` — untrusted fork code (`:34`) — before running `claude-code-action@v1` with `CLAUDE_CODE_OAUTH_TOKEN` (`:41`) and a plugin marketplace fetched from `https://github.com/anthropics/claude-code.git` (`:42-43`). The action's security doc warns against checking out an untrusted ref into the workspace under `pull_request_target`. GitHub does not run files without a `.yml`/`.yaml` extension, so this is **inert today**; renaming it would create a secret-exposure path. The prompt interpolates only `github.repository` and the PR number (`:44`), not attacker-controlled strings.

**F6 — Mutable `latest` tag (Confirmed, Medium for users).** `release.yml:69-73` runs `git tag -f latest; git push -f origin latest` on every stable tag with the `contents: write` token. README/docs tell users to `pip install git+https://github.com/RichardAtCT/claude-code-telegram@latest` (`README.md:52`, `docs/setup.md:53`; mechanism in `docs/development.md:397-401`). A force-pushed moving ref means whoever controls the repo, or anyone with a token holding `contents: write`, can silently change what new installs get; pip does not hash-verify `git+` installs. README advises tagged releases (`README.md:63`), which are themselves mutable refs unless commit-pinned. On this fork `latest` exists only if a stable tag is pushed there; I did not check.

**F7 — Repo identity inconsistency (Confirmed; hijack risk unverified, Low).** `pyproject.toml:26-28` and `src/__init__.py:28` use `github.com/richardatkinson/claude-code-telegram` — HTTP 404 on 2026-11-25 (the user `RichardAtkinson` exists, GitHub id 5873061). README/docs use `RichardAtCT/claude-code-telegram` (`README.md:49,52,58,63`; `docs/setup.md:50,53,59,64,320`; `docs/development.md:20`), which returns **301 → `overwirehq/claude-code-telegram`**. That redirect only holds while the old `RichardAtCT` namespace stays reserved; if it were released and re-registered, `pip install git+https://github.com/RichardAtCT/...` could resolve to an attacker repo (repo-jacking). Whether the old account still exists is **unverified**.

- No `curl`/`wget` in workflows. Network fetches are limited to the actions' own behaviour (F3), PyPI, and GitHub.
- No Docker build/publish, no PyPI publish, no signing/attestation (SLSA/Sigstore); releases are source-only GitHub Releases (`release.yml:60-67`). Absent provenance is a limitation for consumers, not a vulnerability.
- No Dependabot/Renovate config (`.github` contains only `workflows/`), so nothing proposes the bumps in §4.4 or action-SHA updates automatically.

## 6. Runtime tool discovery and environment (F10)

- `find_claude_cli` (`src/claude/sdk_integration.py:45-83`) resolves: explicit config path → env `CLAUDE_CLI_PATH` → `shutil.which("claude")` → globs `~/.nvm/versions/node/*/bin/claude`, `~/.npm-global/bin/claude`, `~/node_modules/.bin/claude`, `/usr/local/bin/claude`, `/usr/bin/claude`. `update_path_for_claude` then **prepends** the CLI's directory to `os.environ["PATH"]` for the whole process (`:88-100`). The resolved path is passed as `cli_path` to the SDK (`:172-178`), so any SDK-bundled binary is bypassed whenever a `claude` exists elsewhere. Abuse prerequisite: write access to a `PATH` entry or `~/node_modules/.bin`, i.e. already local code execution as the bot's user. **Low.** Effective CLI trust is "whatever is on the host", outside this repo's lock.
- Error text tells users to `npm install -g @anthropic-ai/claude-code` (`sdk_integration.py:328`; `src/bot/handlers/message.py:252`) — message text only; the code never runs it.
- `ANTHROPIC_API_KEY` is written into `os.environ` (`sdk_integration.py:144-148`), so the Claude CLI and every tool subprocess inherit it; a prompt-injected tool call can read it. The Telegram bot token is similarly in-process (loaded via `load_dotenv`, `src/config/loader.py:8`, which populates `os.environ`). Mitigation is the Claude sandbox (`sandbox_enabled`, `settings.py:118`; passed at `sdk_integration.py:179-183`); its default value and effectiveness were not verified. **Risk requiring configuration.**
